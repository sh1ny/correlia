An alert’s journey.
From receipt to recovery.

How Correlia takes an Alertmanager delivery, turns it into durable evidence and a live alert, and keeps working when senders repeat, destinations fail or processes restart.

01

One durable core, two independent views.

PostgreSQL coordinates admission, alert state and delivery. NATS is an output—not the internal bus and not required for webhook-only operation.

Reading the map

The worker commits state, activity and output intents in one transaction. The console and output relay then progress independently: a failed destination does not prevent an alert from appearing in the console.

Current boundary: this is alert aggregation and delivery. Incident correlation, incident workflows and Icinga2 ingestion are planned, not shown as running components.

Implementation evidence

docs/ingest-pipeline.md; docs/console-feed.md; docs/runbooks/output-nats.md. Source references are listed with each detail below.

02

A 202 means “stored,” not “delivered.”

The sender posts to /hooks/alertmanager/<source-uuid>. Admission authenticates before consuming the body, bounds the upload, then rechecks credentials inside the storage transaction.

Before the storage write

Bearer token preferred; opt-in path tokens supported. Conflicting credentials, query parameters, unsupported media/encoding and excess body size are rejected. Default/maximum body: 1 MiB; total body deadline: 10 seconds; 16 admission slots.

Two deduplication layers

A source-scoped Idempotency-Key—or source/body digest—reserves a fixed 10-minute transport window. Exact retries return 202; an explicit key reused for different bytes returns 409. Observation deduplication happens later, independently.

Raw rows retain exact uncompressed bytes, digest, receipt time and content type—not raw credential headers. Invalid JSON can receive 202 and later become a durable processing failure. Startup, stopping, saturation or unavailable persistence returns 503 with Retry-After: 1.

Implementation evidence

correlia_server/lib/src/ingest/ingress.dart; ingest/admission.dart; docs/ingest-pipeline.md § Alertmanager sender setup and admission.

03

Validate the batch. Commit its effects together.

A worker pins the active immutable snapshot before processing; a replacement keeps that pin rather than silently substituting newer routes or credentials.

Canonical event

Each alert contributes its own labels, annotations, status and source timestamps. Original selected labels plus source namespace determine identity; Alertmanager’s upstream fingerprint is evidence, not identity. Display truncation never changes the original identity inputs. Structured CloudEvents wrap the canonical payload for outputs.

All-or-nothing work

Validate up to 1,000 alerts before effects. Fold repeated observations; lock fingerprints in sorted order. A bad sibling or fanout above the 16 MiB aggregate bound fails the delivery without partial batch effects. Empty groups complete without events; empty routes are explicitly unrouted.

Transient serialization/deadlock/lock/connection failures retry indefinitely with 1–30-second capped backoff. Other internal failures consume a five-attempt budget before processing_exhausted. Accepted evidence remains inspectable through restricted SQL; there is no public raw-payload or failure-management API.

Implementation evidence

correlia_server/lib/src/pipeline/pipeline.dart; ingest/alertmanager_decoder.dart; event/canonical_event.dart; event/identity.dart; state/alert_state_service.dart.

04

Repeated alerts update state, not incidents.

An alert row is keyed by tenant and fingerprint. Firing → resolved → firing stays the same identity; this is not yet an incident lifecycle.

Why arrival order cannot roll state backward

The ordering fence compares effective source time, receipt time and event id at canonical nanosecond precision. Effective source time is capped at receipt +5 minutes. Evidence at or below the fence is stale: it cannot change the current state.

  • Eligible, visibly different: advance the fence, increment version and append activity. A newer identical view can advance the fence without a version bump.
  • Duplicate observation: retain first evidence; no extra event/output effects. lastObservedAt advances monotonically where eligible.
  • More than 24 hours ahead: quarantine evidence, with no observation key, state or output. Identical quarantine evidence is collapsed.
  • Older than seven days: retain evidence/key, but do not change state or emit output.

The diagram omits unchanged-state self-loops and repeat-resolved updates for readability; the same ordering/version rules apply. Ordinary ready stale evidence can still be retained/routed; “stale” is not the same policy as late, future or duplicate.

05

At least once, with fenced recovery.

Claiming commits an attempt before network I/O. The destination may accept the event just before the worker dies; recovery must then resend the same bytes and event id.

Shared delivery contract

One delivering set per output across workers; independent output lanes prevent one broken sink from blocking healthy ones. A current unexpired claim token fences completion. Expired claims record interrupted attempts and become retryable. Started attempts—including crashes—spend the 20-attempt budget. Backoff caps at five minutes.

Signed webhooks

Exact stored CloudEvents bytes; HMAC-SHA256 signature; Idempotency-Key = event id. Only 2xx acknowledges. Network errors, timeout, 408, 429 and 5xx retry. Other statuses, including redirects, are permanent; redirects are never followed. Calls have a 10-second total deadline.

Consumer obligation: deduplicate by event id. Delivery is not exactly once and is not ordered per alert. Queued work never switches to a newer destination definition after config rotation. Delivered/dead rows have no automatic replay.

Implementation evidence

correlia_server/lib/src/output/output_relay.dart; output/relay_subsystem.dart; output/webhook_output.dart; docs/ingest-pipeline.md §§ Plugin batch delivery, Signed webhook delivery and recovery.

06

The plugin is a process. JetStream owns storage.

The first-party Go output-nats executable runs behind Correlia’s gRPC plugin boundary. It connects to an operator-provisioned stream; it never creates or modifies streams.

Host supervision

Owner-controlled executable directory and pinned SHA-256; private startup handshake and secure RPC; secret bytes delivered separately during Configure. Only a ready instance serving the pinned definition can claim its rows. Batches are bounded to 64 events / 1 MiB, further reduced by negotiated limits; all outcomes finalize together. The NATS plugin permits one outstanding batch and bounds its publish acknowledgements to ten seconds.

Instances restart with 1–60-second backoff. More than five failures in ten minutes opens a degraded circuit; probes run every five minutes. Missing historical secrets leave that definition queued without new attempts.

Broker contract

Subject: correlia.v1.ev.<tenant>.<kind>.<source_kind>.<severity>. The exact CloudEvents body is preserved; Nats-Msg-Id = event id. The expected stream is asserted on publish. Success requires a JetStream storage acknowledgement, including a duplicate acknowledgement.

Broker deduplication only covers its configured window. Consumers still need durable event-id deduplication for recovery outside that window. A broker ACK says nothing about a consumer having processed the event.

Implementation evidence

correlia_server/lib/src/plugin/plugin_host.dart; plugin/plugin_supervisor.dart; plugin/output_plugin_connection.dart; plugins/output-nats/; docs/runbooks/output-nats.md.

07

The feed—not the socket—is the source of truth.

Snapshot rows and cursor share one repeatable-read snapshot. Feed pages carry ordered activity plus current alert views, which can already be newer than their activity entry.

While the app stays open

The wakeUps stream carries notifications, not entries. API watermark polling runs at least every 500 ms while subscribed. On a wake-up, and every 10 seconds even with a live socket, the client pulls the feed. Partial lists periodically refresh their snapshot bounds. A dropped stream reconnects and resumes from the last retained cursor with 1, 2, 4, then 10-second retry backoff; an invalid cursor requires a fresh snapshot. Resolved rows leave the list; version tombstones prevent old responses from resurrecting them.

Ordering without lost commits

The server only exposes activity below the oldest-active-transaction watermark, so a late commit cannot be skipped. heldBack means more committed activity is temporarily fenced. Merge current alert views by version; duplicate activity already represented by the snapshot is legal.

Current surface: a live firing-alert list, not an activity-ledger UI or incident workspace. It provides a local text filter, severity chips, source links, partial-list indicators and live/disconnected status. Snapshot is capped at 500 firing alerts with omittedCount; feed pages clamp to 1–1000. Console endpoints are unauthenticated and restricted to loopback peers/Host/Origin, development/test mode and api/all roles. Do not expose this console as a production interface.

08

Long-running means durable work, not immortal processes.

The same Dart/Serverpod binary runs api, worker or all (default). PostgreSQL row locks, claims and leases coordinate workers; no in-memory queue is authoritative.

Role ownership

api: webhook admission, console reads and feed wake-ups; future-call execution disabled. worker: ingest workers, plugin host and output relay; generated RPC endpoints remain on its API port but console access is refused. all: both sets.

Configuration over time

Public snapshots are immutable; only strictly newer unseen revisions can replace active config. Identical active content is a no-op. Revert by publishing the desired content under a higher revision. Source rotation has no overlap window. Historical queued outputs retain their original definition and secret commitment.

What an operator must still plan

There is no raw/event/activity retention or partition-maintenance scheduler, automatic dead-letter replay, disk-pressure/backpressure policy, production console auth, or incident correlation in this implemented slice. Plan disk headroom and preserve historical output credentials while live work uses them. SQL schema steps and Serverpod migrations must both ship; inspect repair migrations so they do not drop SQL-owned evidence tables.

The ten-minute transport deduplication window is an expiry comparison, not a cleanup job: distinct transport keys still accumulate. Raw evidence, events, output rows, attempts, observation keys, transport keys, failures and activity have no automatic deletion here. Correlia also creates no durable JetStream consumer; the development subscriber is live-only, not a replay tool.

Graceful stop closes acquisition, drains relays and stops plugins before database closure. A kill can leave started delivery attempts; lease expiry makes them recoverable. Plugin supervision cleans its own status history—this is not event-data retention.

The honest boundary

What exists—and what does not yet.

Implemented now Planned / not implemented in this slice
Alertmanager v4 webhook admission; canonical events and CloudEvents; immutable source/output config. Icinga2 ingestion, richer enrichment and the broader integration catalog.
Durable raw inbox; observation identity; fenced firing/resolved alert state; atomic activity and outbox writes. Incident grouping/correlation, acknowledgement workflows, silences, maintenance, inhibition and flapping logic.
Signed webhook output and supervised NATS JetStream plugin; leased retries, dead outcomes and crash recovery. Operator replay workflow, event-data retention, partition maintenance and disk-pressure/backpressure policy.
Local, unauthenticated development/test firing-alert console with snapshot/feed synchronization. Production auth, RBAC, incident workspace and configuration-management UI.

Implementation and milestone acceptance are separate. Correlia-authored automated fixtures are not live upstream captures; the owner's real-Alertmanager milestone-close demonstration remains a separate check. This guide is a dated snapshot, not a promise that later code still matches it.
