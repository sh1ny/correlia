PLG-03: Structured Notification Outcomes

Date2026-07-10 Input shapeconcept SubjectCorrelia Phase 9 requirement PLG-03

The requirement in one sentence

PLG-03 says a plugin failure must become data, not merely a log line.

Notification dispatch converts plugin exceptions into structured NotificationResult records instead of relying on logs alone.

This matters because background delivery is detached from the ingress request. If an email plugin fails after ingress has already returned, the original caller cannot learn that from the HTTP response. Correlia therefore needs a bounded, queryable outcome attached to durable incident state.

Two results exist at two different times

1. Immediate: task submission

Owned by Icinga2DecisionProcessor. A successful result means the in-process runner accepted and scheduled the task.

success: true
category: dispatched
message: "notification task submitted"

It does not mean SMTP or another plugin completed.

If a selected plugin cannot produce a task because the plugin or runner is unavailable or submission raises, that immediate failure is terminal. Phase 9 persists the same safe failure after the incident commit; an accepted submission remains response-only until the dispatcher completes.

2. Eventual: plugin delivery

Owned by NotificationDispatcher. It is produced only after the background handler invokes the output plugin.

success: false
category: plugin_exception
message: "plugin exception: RuntimeError"

PLG-03 primarily governs the dispatcher result, plus terminal ingress failures for which no delivery task can exist.

What “structured” means here

A NotificationResult has a closed shape rather than arbitrary exception text:

  • success: boolean.
  • category: one of dispatched, missing_plugin, missing_incident, plugin_exception, or dispatch_failed.
  • message: non-empty and capped at 256 characters.

When a plugin raises, Correlia catches the exception, records only its type, increments bounded metrics, and persists a safe result. A secret-bearing exception such as RuntimeError("password=...") becomes plugin exception: RuntimeError; the raw message and traceback are not placed in operator-visible state.

Logs remain useful diagnostics, but they are no longer the only truth. An operator can inspect the incident and see plugin, category, success, and safe message facts after background completion.

Current storage before Phase 9 convergence

Correlia stores eventual outcomes inside Incident.decision_context.notes. One outcome consumes four note entries:

notification.0.plugin   = "email-oncall"
notification.0.category = "plugin_exception"
notification.0.success  = "false"
notification.0.message  = "plugin exception: RuntimeError"

A successful result also sets Incident.notified_at. A failed result leaves it unset. This keeps notification observability incident-local and avoids introducing the durable delivery/outbox machinery deferred to FUT-01.

The Phase 9 retention decision

Approved: use a dedicated, bounded latest-result collection inside DecisionContext.

The current flattened notes remain the defect being replaced. Four note keys only approximate one record, compete with unrelated incident notes for the same 20-entry budget, and can be partially or completely evicted.

Target contract: notification_delivery_results holds at most 20 complete records, one latest terminal submission-or-delivery result per selected output plugin.
An accepted task is not yet terminal; general notes have independent capacity and are never evicted by notification outcomes.
{
  "notification_delivery_results": [
    {
      "schema_version": 1,
      "plugin_name": "email-oncall",
      "result": {
        "success": false,
        "category": "plugin_exception",
        "message": "plugin exception: RuntimeError"
      }
    }
  ]
}
  • A valid rule may contain at most 20 actions, and each action must reference a distinct output plugin.
  • When submission fails or delivery completes, recording the same plugin replaces its prior terminal result; this is latest state, not attempt history.
  • A 21st distinct record is rejected rather than truncated or evicted.
  • Later incident aggregation and a fresh application runtime must preserve and expose the records.
  • Historical flattened notification.N.* notes remain readable, but new terminal outcomes write only the dedicated collection.

This is the middle boundary: stronger than bounded best-effort notes, much smaller than a notification-attempt table or outbox. If the process exits after accepting a task but before dispatch completes, the task and result can still be lost; crash recovery, attempt identity, timestamps, retries, queue ownership, and delivery history remain FUT-01 work.

What Phase 9 must prove

  1. Rule startup accepts 20 distinct plugin references and rejects a 21st action or a duplicate plugin reference.
  2. A missing plugin, unavailable runner, or raising task submission returns and persists one safe terminal failure without creating a task.
  3. A deliberately slow plugin remains blocked while ingress returns only a task-submission result.
  4. After release, each success or safe plugin_exception becomes one complete dedicated record.
  5. Twenty plugin records coexist with general notes without truncation or eviction.
  6. Re-recording one plugin replaces only that plugin's latest terminal state.
  7. Success sets notified_at; failures alone leave it unset and never clear another plugin's success timestamp.
  8. Later aggregation, PostgreSQL JSONB decoding, and a fresh application runtime preserve the collection.
  9. The canonical incident endpoint exposes every field without requiring logs or silently blanking strict decision context.

PLG-03 still does not require retries, a broker, an outbox, extra transports, or delivery to block ingress. It requires terminal outcomes from the existing output-plugin boundary to become safe, bounded, complete, incident-local domain facts without pretending accepted work is completed delivery.
