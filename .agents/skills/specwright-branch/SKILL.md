# Specwright Branch

Insert a branch gate in front of the vanilla change-creation workflow. Run no OpenSpec command that writes until the gate passes (`openspec list --json` only reads). Stop and ask at every failed check; never proceed silently.

**`<sw>`.** Specwright's own work runs in one binary, `sw`, which the install prompt places. Read `openspec/.specwright/VERSION` in the code checkout; it must be `x.y.z` with an optional `-<pre-release>` and `+<build>` suffix and nothing else. Any other value (a path, a space, an empty file, no file): stop before building any path and tell the user to rerun the install prompt. `<sw>` is `<home>/.specwright/bin/<VERSION>/sw` (`sw.exe` on Windows); `<home>` is `SPECWRIGHT_HOME` when set, else the user's home. Never run an `sw` found on `PATH`, another version's binary or a copy elsewhere. When that file does not exist, stop the step and tell the user to rerun the install prompt. Before the first other `<sw>` command of a run, run `<sw> version --json` with a 10-second tool timeout and stop unless it exits 0 in time and prints one JSON object whose `version` is `<VERSION>` and which reports interface 3: on any other result run no other `<sw>` command and tell the user to rerun the install prompt. A project at an older version, whose binary reports interface 2 or 1, stops the same way; tell the user to update this project. Any `<sw>` command that prints a `sw_mismatch` document (the binary and the project's `VERSION` differ) stops the step the same way, showing its `message`. Every `<sw>` command prints one JSON document unless its section says otherwise.

1. **Planning repo** (below) first: a stop there creates no branch. **Inspect** the code repo with `<sw> vcs state`. Every `<sw> vcs <sub>` call below takes `--repo <toplevel> --role code` for the code repo, and for the store `--repo "<store toplevel>" --role store --code "<code toplevel>"`, which the text leaves out; every call prints one JSON document with `ok` and `backend` (`git`, `jj` or `gitbutler`), a stop adds `error` and `message`. `state` gives `branch`, `main`, `on_main`, `clean`, `dirty_paths`. Error `not_repository` → stop and ask (recommend abort); any other `error` (`tool_missing`, `tool_too_old`, `not_managed`, `not_colocated`, `target_mismatch`, `unsupported_vcs`, `unsupported_combination`, `gitbutler_workspace`) → stop and show its `message`: the repo asks for `vcs: jj` or `vcs: gitbutler` and is not ready (GitButler runs only for the code repo with `finish: pr`; the gate never sets GitButler up). On Git with `jj_present: true` the repo holds jj metadata but `vcs: jj` is not set: say once `this repo has jj metadata; set vcs: jj in openspec/specwright.yaml to route writes through jj`, and go on with Git; it is a note, not a stop.
   - **GitButler tool guidance.** With `backend` `gitbutler` the probe passed, so the repo is already managed. Load the `gitbutler` skill (GitButler's own) for how `but` works; Specwright ships none of its own, and every write still goes through `<sw> vcs`. Load it from wherever the agent finds it. Then run `but skill check --local --json` once in the code repo (never `--update`, which rewrites files). When it reports the skill missing or out of date, add a note that GitButler's agent skill is missing or out of date in this project, with the install command `but skill install --path <agent skills dir>/gitbutler` (the install prompt offers it), and go on: it is a note, never a stop, and the gate installs nothing (the install prompt offers it and runs it only on the user's yes).
2. **Change name:** use the user's kebab-case name verbatim; otherwise derive one from the description (lowercase, spaces to hyphens, drop other characters). This name is authoritative: pass it verbatim to `openspec new change` and the triggering workflow; never let them derive another.
3. **Main branch:** `<sw> vcs state` reports `main` (`main_branch` in `openspec/specwright.yaml`, else `main`, else `master`); none of them exists → ask.
   - **Used once:** an earlier change may have been merged from another checkout, so refresh the planning repo's main first when it has an `origin`. Read its fetch URL with `git remote get-url origin` (not its push URLs): when that URL is on github.com (any scheme; `github.com.` counts as github.com), run `<sw> vcs fetch-main --quiet --login <login>`, decided by the fetch URL and not by `<sw> pr identity`, which reports a mismatch for an origin that pushes to a fork; on any other host run `<sw> vcs fetch-main --quiet`, which runs plain. `<login>` is the one this gate was handed (`run login: <login>`, as `specwright-roadmap` **next** does), otherwise `github.login`, else the one `<sw> as --resolve` prints, once, for this gate only when it is user-started; a handed login is never resolved again, and a handed `run login: none` (no gh account) means local refs only, with no `--resolve`. When planning is in a store, its fetch takes the store login, `planning_store.login`, else that run login (resolved only when it is needed). A refusal (exit 3, including a failed `--resolve`: no gh account) or a failed fetch is not a stop: say `local refs only (no gh account)` and continue on local refs. The fetch moves only the remote's main and prints its `ref`: `origin/<main>` on Git, a commit id on jj and on GitButler (read the archive on that commit, not on local `<main>`, which can lag a pull that was skipped). Then list its archive on `<main>` and, when the fetch succeeded, on that `ref` (`git ls-tree -d --name-only <ref> -- <P>/changes/archive/`; read-only Git works on jj too), with the planning repo's main: this step's main when planning is in this repo; when store-backed, run it in the store with the store's main (`planning_store.main_branch` in this repo's `openspec/specwright.yaml`, else `main`, else `master`, as in store step 2). An entry named `<change-name>` or `YYYY-MM-DD-<change-name>` means a change of this name was already archived → stop, since PR, merge and archive proofs match changes by name and would take the earlier one for this one. Offer another name (suggest `<change-name>-2`) or abort.
4. **Not on main** (`on_main` false) → stop. On GitButler `state` is read without `--branch` here, so `on_main` is true and this step passes; other applied branches are not a stop, and the gate never switches or unapplies one. Offer: switch to main (`<sw> vcs switch --branch <main>`, only if the tree is clean apart from step 5's carry-over), or abort.
5. **Dirty tree:** `dirty_paths` only under `<P>/changes/<change-name>/` are this change's artifacts, created before the gate ran (or when apply found the change on main): they carry over to the new branch, so continue. Anything else → stop and show those paths. **On GitButler this is no stop**: edits of other applied branches and unassigned edits stay where they are, so continue, and list those paths once as `changes this change will not commit` (they are not part of this change; never stash, move or commit them). One exception: `<sw> vcs` stops with `settings_not_pinned` when another applied branch changes `openspec/specwright.yaml` (committed, or an edit assigned to it), because every step reads the settings from the shared work tree; show the message and stop until that branch is unapplied or the edit moved. Offer: commit first or abort. Commit first commits those paths on main, only on the user's yes and with a message they approve: `<sw> vcs commit --branch <main> --message-file <file> -- <those paths>` (Git and jj alike; an install's own setup files are the usual case), then run the gate again. On the Git backend also offer stash (`git stash push -u -m "specwright-branch: pre-<change-name>" -- <those paths>`, report the ref). On jj never stash, and never offer it: jj has no stash, and its working copy follows the branch.
6. **Prefix** from the name's first token: add/feat/feature/implement/introduce → `feat`; fix/bugfix/hotfix/patch/resolve → `bugfix`; refactor/restructure/cleanup → `refactor`; docs/doc/document → `docs`; chore/bump/deps/ci/build → `chore`; anything else → `feat` (say so in one line).
7. **Existing branch** `<prefix>/<change-name>` (a local branch, on jj a bookmark: `git rev-parse --verify` sees both) → stop (store-backed: note it and go on; store step 2 decides once both repos are inspected). Offer: switch to it and resume the change (do not re-scaffold), pick another name, or abort.
8. Store-backed → continue with **Store-backed changes** (below) instead of this step. Otherwise `<sw> vcs branch-create --branch <prefix>/<change-name>` (on GitButler it creates and applies the branch on the target beside the branches already applied, and leaves them applied; a branch of that name that exists but is not applied stops with `branch_exists`: offer resume, another name or abort), announce `On branch <prefix>/<change-name> (from <main>)`, then hand back to the triggering workflow. If the change directory already exists, tell the workflow to continue it rather than create it again.

If the roadmap (`project.roadmap`, default `openspec/roadmap.md`) exists and the user did not say which milestone this change serves, ask, so the proposal can name it.

One working tree holds one change at a time: this skill switches the branch of the whole checkout. When several agents work on the project at once, each change needs its own `git worktree`. On GitButler it does not: several change branches are applied in one working tree, each commit names its branch and paths.

Never commit or push here.

## Store-backed changes

When the **Planning repo** is a store, the gate covers both repos and both get the same branch name. Steps 1–7 run on the code repo as written, except that an existing branch in step 7 is only noted: whether it stops depends on the store too. Then:

1. **Lock** the store gate before touching the store: `<sw> --project "<code toplevel>" gate lock --store "<store toplevel>" --branch <change-name> --code "<code toplevel>"` (`--project` names the code checkout, because the store holds no `VERSION` of its own). It takes the lock atomically, so two sessions cannot both hold it, and prints `"ok": true` with the lock's `token`: keep that token, the release needs it. When it succeeds, you hold the lock: go on to step 2. A `gate_locked` document means the lock is held: stop before touching either repo, show its `owner` (when the lock was taken, for which change, from which checkout) and say another session may be in its gate for this store. When the owner's `change` starts with `specwright-update`, a store update holds the lock instead: say an update from the checkout on its `code` field holds the store, tell the user to rerun the update from <code> (that `code` field), and do not offer removal (the stale removal refuses it with `gate_update_held`). For every other holder, a lock left by an interrupted session is never removed automatically: run `<sw> --project "<code toplevel>" gate show --store "<store toplevel>"`, show the owner and its time, and ask the user to confirm that no other session is in its gate. Only on that confirmation remove it with `<sw> --project "<code toplevel>" gate unlock --stale --store "<store toplevel>" --token <the token `gate show` printed>` (`--ownerless` in place of `--token` for a lock with no owner token), then rerun the gate. When the user does not confirm, remove nothing, create no branch in either repo, and leave the lock and its owner as they are. A `gate_not_owner` answer means the lock changed after the confirmation: show it and ask again.
2. **Store checks**, with the lock held: run steps 1, 3, 4, 5 and 7 on the store (`<sw> vcs` in its store form; the store's `state` probes the store's own backend, so a `planning_store.vcs: jj` store without `.jj` stops here with the lock held, before any branch exists; read-only Git runs with `<store toplevel>` as the working directory). Main is `planning_store.main_branch` in this repo's `openspec/specwright.yaml`, else `main`, else `master`. Step 5's carry-over is `<P>/changes/<change-name>/` in the store.
   - Store on another change's branch → **busy**: stop, name that branch, and say one store holds one change in progress at a time on this machine (finish or archive that change first). Do not offer to switch it.
   - Store dirty → stop and show the store's `git status --short`, with the same offers as step 5, run in the store.
   - **Store version:** read the project's `<code toplevel>/openspec/.specwright/VERSION` and the store's `<store toplevel>/openspec/.specwright/STORE` with your file tool (`STORE` is two lines, `version: <x.y.z>` and `owner: <id>`), and compare `major.minor` only. No `STORE` record passes. An unreadable `STORE` (it exists but has no version or no owner) or a missing `VERSION` (no completed install in this project) → stop: a missing `VERSION` names the store's version and says to run the install in this project, or the update when it already has one. A missing `VERSION` stops at the top of this skill, before any lock is taken, because `<sw>` cannot be built without it. A mismatch → stop, naming both versions and the owner: project behind the store → update this project to the store's `major.minor`; store behind the project → the store's owner updates the store first. Each of these stops, and a store probe error, releases the lock first (step 4).
   - `<prefix>/<change-name>` exists in both repos → stop with step 7's offers.
   - `<prefix>/<change-name>` exists in only one repo (the code repo's, noted in step 7, or the store's) → stop. Offer to resume it and create the missing one, pick another name, or abort.
3. **Create** only after both repos pass: `<sw> vcs branch-create --branch <prefix>/<change-name>` in the code repo, then in the store. If any `branch-create` errors, in the code repo or the store, roll back before anything else; a failing `post-checkout` hook makes it error after the branch was created and switched to, so never assume nothing was made. In each repo where this gate ran `branch-create` and `<prefix>/<change-name>` exists: on jj (`state` shows `backend` `jj`), switch nothing: `branch-create` only added a bookmark at main's commit, which `state` reports as the current branch until it is gone, so delete it with `<sw> vcs delete-branch --branch <prefix>/<change-name>` and judge it by `state --branch <prefix>/<change-name>` (`on_main` true). On GitButler (`backend` `gitbutler`) switch nothing either: delete the branch the same way (it holds no commit, so the delete needs no merge proof) and judge it by `state --branch <prefix>/<change-name>` (`on_main` true); the other applied branches stay applied. On Git, when `<sw> vcs state --branch <prefix>/<change-name>` shows the repo on `<prefix>/<change-name>`, run `<sw> vcs switch --branch <main>` (that repo's main) and ignore its exit status (the same hook may fail again), then judge the switch by `state` (`branch` is `<main>` or `on_main` is true), not by the exit status; once it is, delete the branch with `<sw> vcs delete-branch --branch <prefix>/<change-name>` (nothing is committed on it). A repo still on `<prefix>/<change-name>` keeps it: delete nothing there, but still roll back the other repo. Then release the lock (step 4) and stop, showing the original error; when a repo could not switch back, name that repo, `<prefix>/<change-name>` and its main.
4. **Release** the lock right after both branches exist, with the token step 1 printed: `<sw> --project "<code toplevel>" gate unlock --store "<store toplevel>" --token <token>`. It removes the lock only when its owner holds that token and answers `gate_not_owner` for anyone else's, which you leave alone. Every stop from step 1 onwards releases it first, unless the stop is that the lock was held by someone else.
5. Announce `On branch <prefix>/<change-name> in the code repo (<code toplevel>, from <main>) and the store (<store toplevel>, from <store main>)`, then hand back to the triggering workflow. It scaffolds the change in the store, since the root resolves there.

Once a store branch exists, any later gate sees the store as busy, so the lock only covers the gate itself.

## Planning repo

OpenSpec decides where planning lives: in this repo, in a folder nested in it, or in a store (a separate git repo). Resolve it at the start of every run, before any write; never assume `./openspec/`.

1. **Root:** `openspec list --json` from the code checkout, plus `--store <id>` when the session selected a store. It needs no change name, writes nothing and still works after archive. `root` null with an error whose `message` starts with `Declared in` or `Invalid store declaration in` → stop before any git or file write and show that `message` and `fix`.
2. **Repo**, in two calls: `git rev-parse --path-format=absolute --git-common-dir --show-toplevel`, then `git -C "<root.path>" rev-parse --path-format=absolute --git-common-dir --show-toplevel`.
   - The second fails (root not in a git work tree) → stop and ask: initialise git there, or abort.
   - Different common dir → **store-backed**: the planning repo is the store checkout at its toplevel.
   - Same common dir and toplevel → **repo-local** (including a root nested in this checkout, such as `planning/`): one repo, as before.
   - Same common dir, different toplevel → the root is in another worktree of this repo, where a commit would land on that worktree's branch. Stop before any write, name both worktrees (path and branch) and ask.
3. Announce once: `Code repo: <toplevel>; planning repo: <toplevel> (store <root.store_id>)` or `(same repo)`.

**Paths.** `<P>` is `<root.path>/openspec` made relative to the planning repo's toplevel (`openspec` in the usual layout, `planning/openspec` for a nested root). Stage and `ls-tree` planning files as `<P>/...` in the planning repo.

**Where commands run.** Git, `gh`, `<sw> as` and `<sw> vcs` commands on the store run with `<store toplevel>` as the working directory, changed into in the same call because the directory does not carry to the next one (`<sw> as` only fences the repo it starts in; from the store it takes `--project "<code toplevel>"`: `<sw> --project "<code toplevel>" as <login> ...`). `openspec templates` and `openspec schema validate` have no root selection: run them with `<root.path>` as the working directory in the same way. `git -C` is for read-only queries only (`rev-parse`, `status`, `log`, `ls-tree`).

**Archive name.** Use `archivedAs` from the archive output when you have it. Otherwise it is the change name if that starts with `YYYY-MM-DD-`, else `YYYY-MM-DD-<change-name>`: `<P>/changes/archive/<archived-name>/`.

**Referenced stores.** A `references:` list in the root's `config.yaml` does not move the planning root: a repo with its own root stays repo-local. Referenced stores are read-only: never branch, commit, stash, push, open a PR or write a file in one. Read them only through `openspec context --json` (each `members` entry with `role: referenced_store` gives its `path` and a `fetch` command such as `openspec show <spec-id> --type spec --store <id>`). A member whose `status` has `reference_unresolved` (the store is not registered on this machine) is named in the report as `unresolved reference: <id>` with its `fix`, and the step continues without it; never guess its path.
