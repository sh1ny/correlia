## Findings

### Critical (blocking)

1. **Distinct check starts can collapse to the same fence time inside the claimed convergence domain.** D1 argues that flooring is monotone. It is not *strictly* monotone: at contemporary Unix times, two binary64 starts can be 238 ns apart and floor to the same microsecond. If the later-start OK arrives first and the earlier-start CRITICAL arrives later, `ordering_key.dart:43–51` gives the CRITICAL the higher fence by receipt time. Both results can be recent and unclamped, and D17 gives them distinct IDs; still, the alert ends firing until another eligible observation repairs it. The equal-start scenario does not cover this: the upstream starts are unequal. Preserve sufficient precision in the fence or narrow the guarantee to strictly increasing **projected** starts. Test reversed receipt of two distinct starts in one microsecond, including fence reload.

2. **An old stream copy can reserve the ID of an eligible recovery and prevent sync from repairing it.** Start with a firing alert. Admit an OK promptly on the stream but leave the row pending. More than seven days later, a stream copy of that same result arrives late and is processed first. `pipeline.dart:445–495` inserts its `late` key before effects, then treats the promptly received copy as a duplicate, so the alert never resolves. The existing `integration-icinga2` scenario “Late reminder wins the event-ID insert” already proves this behavior for webhooks. D2's exception for **late reconcile** items does not prevent late **stream** items from reserving the shared ID; choosing `execution_start` only fixes the archived case where the checks were different. Define which evidence owns the state effect and which owns publication when readiness differs across copies. Test both processing orders with a firing alert and assert state, key, event and sync outcome.

3. **D12 still has no consistent end to a sync or enforceable resync deadline.** If the first batch fails while enumeration is still running, D12 says mark the sync `failed` immediately. Starting the replacement then overlaps the old enumeration; waiting for it to end can take 15 minutes, contradicting “Valid sync row fails in the pipeline,” which requires a replacement within five minutes. Waiting for all application to finish instead can block indefinitely: the base pipeline explicitly retries transient failures without consuming the attempt budget (`pipeline.dart:740–816`), including while the database remains reachable. The `resyncRequestedAt` set/clear protocol also loses a request if `_fail` commits between the holder's observation of the old request and its unconditional clear. Define separate admission and application boundaries, a terminal outcome for blocked application, and an atomic request acknowledgement that cannot erase a later request. Test early failure during enumeration, indefinitely pending application on a reachable database, and the concurrent set/clear.

4. **The proposed shutdown cannot guarantee lock release and can terminate unrelated pooled work.** D13 waits until second four before launching termination on a separate connection whose acquisition alone may take one second. It leaves no time to confirm termination and cannot reach the backend at all during a database network partition. A transaction that just took its last lock can outlive the advertised five-second stop bound even with D5's five-second idle timeout. There is also a race between deciding to terminate and signaling the recorded PID: the transaction can finish and return that same backend to the pool, where it can begin unrelated work. Finally, D13 limits termination to embedded PostgreSQL; `config/production.yaml` specifies external PostgreSQL. Define a cancellation mechanism that owns the connection through cancellation, and distinguish local stop from database lock release when the database is unreachable. Prove both contracts on the supported production path with independent connections, including pool saturation and completion racing cancellation. The 10-second worker budget must cover all consumers, not 10 seconds per source.

5. **Lease expiry is not the write boundary promised by the spec, and a delayed renewal reply can leave two live readers.** D4 checks expiry after taking `FOR SHARE`, but a transaction can pass the check at second 29 and commit at second 31; the share lock blocks takeover, not expiration. D5's per-statement limits do not change that. Separately, if a renewal sets expiry at database time 30 and its success reaches the holder 12 seconds late, a new 20-second local deadline measured from receipt lands at second 32. A replacement can subscribe at 30 while the old process is running, not frozen. State whether a transaction authorized before expiry may finish after it, and anchor the local deadline conservatively to the renewal attempt rather than the acknowledgement. Test delayed successful renewal and expiry between the last lease check and commit.

6. **The retained-work cap bounds a stalled pipeline, not a healthy one filling the database.** D7 stops at `pending + failed`; `done` rows are excluded. The design itself projects 1,000 completed sync rows per hour for one 100,000-object installation, even with no changes or published events. A fast pipeline can keep the cap near zero while successful syncs consume shared PostgreSQL storage. ADR 0016 requires pull sources to pause at the storage watermark; D7 defers it, while the ADR section claims no supersession. Require the storage guard before enabling this source, or obtain an explicit exception with a measurable interim storage bound. Test a source below its pending cap at the database watermark.

7. **One persistent bad sync object can indefinitely prevent a later valid recovery from being read.** D3 fails enumeration on a malformed or oversized element or an upstream per-object error. The state machine closes the subscription and restarts the same queries from the beginning. If a persistent error sorts before a service whose recovery was missed, that service is never read on any retry—even when its result is eligible and otherwise valid. The truncated-prefix scenario proves preservation of earlier work, not reconciliation of later objects. Specify whether a per-object error allows safe continuation with a failed or partial outcome, or state that it blocks reconciliation and expose the affected scope. Test a persistent invalid object followed by a valid missed recovery.

8. **The historical reuse backfill misses bare credentials and can miss signing commitments.** D8 seeds from `ingest_secret_commitment` and “the pins.” `config_repository.dart:186–246` writes only output commitments to that table and deletes/replaces live credential rows at publication. Historical credential digests are in immutable `ingest_config_snapshot.publicJson` (`source_config.dart:34–40,112–126`; `bootstrap.dart:163–171`). A removed credential with no live pin therefore has a durable bare hash but is not named as a backfill input. A webhook signing commitment can likewise survive only in a historical snapshot when the commitment row for a shared reference is keyed. A subsequent password publication can pass with bytes whose bare digest is already stored. Enumerate the authoritative historical sources explicitly and seed from them before the first password publication. Test a populated upgrade with a removed credential and a removed webhook signing use under a shared keyed reference.

### Moderate

1. **The fanout bound does not use the cited pipeline formula or the pinned routing.** `pipeline.dart:547–555` charges one canonical payload plus one per routed output for ready evidence, not payload times route count. A zero-route source still incurs one payload per item. D6 sizes against the consumer's active routes, but `pipeline.dart:261–297,351–383` selects routes at first claim, and D15 adopts route changes without reconnecting. The proposed load test therefore does not prove the stated headroom across a publication. Bound each batch against the pipeline formula and a route count that remains valid until claim, then exercise an increase in routes between admission and pin.

2. **Sync completion has no bounded, durable accounting path.** D12 puts the sync ID in raw bodies and polls for outcomes. D5 defines no indexed membership or durable expected count. A body scan every 30 seconds grows with inbox retention; counting only existing rows cannot distinguish “all admitted rows succeeded” from “some were discarded or pruned before the poll.” The raw outcome delta also excludes `diverged` from row counters without saying how the holder durably learns it from a pipeline transaction. Define how completion and counts survive retries, terminal-row deletion and takeover without scanning unrelated raw payloads. Test deletion or discard before the final status poll.

3. **Status and gap requirements contradict their actual writers and retention.** “Every status write” requires a live lease, but the pipeline must set `resyncRequestedAt` atomically with failure and owns no lease. A failure can also occur before a status row exists or after retirement. Separately, pruning a gap ID after 30 days removes the only evidence used to reject a later retry, while the spec promises exact-once counting with no retry horizon. Specify the pipeline-owned field and initialization rules separately. Either constrain legal gap writes to a durable sequence or bound the replay contract; do not retain a per-connection ledger while promising an invariant that its pruning invalidates.

4. **Several modified requirements leave opposing baseline rules in force.** The base `durable-pipeline` requirement “Rows decode by their source's kind” remains unchanged, while the addition says dispatch by stored format. The base `alert-state` requirement “Resolved alert fences late evidence after its events expire” still mandates storing previously unseen late firing evidence, which the reconcile delta forbids. The base `secret-store` requirement “Secret bytes never leave their consumer” lists permitted consumers but is not modified to include stream authentication and publication's reuse check. Amend the affected requirements and make ADR 0030 explicit about its exceptions to ADRs 0016, 0017 and 0024, particularly unknown-commit retries without a transport key and reconcile effects without an observation key.

5. **The guarded-parser and resource evidence does not establish the new boundary.** The webhook parser's `_repeatedMember` checks only depth 1 (`webhook_parser.dart:228–260`); state-bearing fields now live inside `check_result.vars_after`. Reusing that guard unchanged accepts duplicate nested state members. The existing parser also reports `duplicate_field` and maps UTF-8 decoding failures to `invalid_json`, not the delta's distinct codes. Specify the nested guard and persisted diagnostic rules, including a nested dotted unknown member and duplicate state. For D7, distinguish a reader waiting normally for data from one prevented from draining: “not read for 30 seconds for any reason” is also true of a healthy quiet subscription if interpreted as elapsed time since the last read. Test both a quiet connection and a blocked reader with an injected clock.

6. **Configuration adoption covers existing consumers but not discovery, and the default mode can invalidate identical old bootstrap input.** D15 has each consumer check its own revision. A worker started with zero stream sources has no consumer to discover a source published later. Also, `bootstrap.dart:163–171` hashes serialized source fields into the snapshot ID, and `config_repository.dart:135–150` rejects different content at the same revision. Adding an explicit `mode: webhook` to the serialization of existing sources would therefore reject the same old config on upgrade, despite the proposal's compatibility promise. Assign ownership of source-set reconciliation and specify whether default mode preserves old snapshot bytes or requires an explicit revision bump. Test zero-to-one publication on a running worker and restart with an existing webhook snapshot.

7. **The evidence and acceptance map are not complete.** D1's reversal-cost paragraph says captures “confirm” the evidence on every supported release, while A1 says none has run. D16 allows excluding a failing release, but “Version matrix” names all four minor releases and can be read as requiring all four. Pin the matrix to the declared supported set and include a failing-gate case for a listed release. The review-response table also says the roadmap update is in tasks; no `tasks.md` or scenario-to-task map is present, and `openspec/roadmap.md:42` still lists `CheckResult`. Map real-release permissions, first-sync status, cancellation and other reproducible scenarios to automated evidence. Leave only the real-installation day-long run with the owner.

8. **Carried constraints omit decisions that subsequent changes can break without touching the new specs.** C1 preserves the source fields but not the frozen D11/D17 key encoding; a later mapper could change number text and republish the same evidence under new IDs. No entry carries D10's distinction between policy-skipped results and keyed informational events, so a later change could reintroduce the cross-policy dedup failure. C2 also says committed batches are never resent, although the failure table explicitly retries an unknown commit outcome. Give the identity encoding and policy omission one destination each, and state the actual retry exception in C2.

## Rebuttals

Round 1's silent tombstone, standalone cross-policy skip, short service-name projection, per-item receipt evidence, local-only endpoint scope and owner attribution for D5/D9/D10/D17 are present. The new raw envelope also represents the malformed inputs that round 1 identified. The original clamp and lateness examples are now documented, but precision and shared dedup leave the convergence guarantee false. The retained-work, shutdown, lease, sync-completion, historical-secret and gap remedies are partial; the remaining counterexamples are above.
No finding is rebutted; each is fixed in round 3 (design.md, "This change's review round 2"):

  equal starts").
- C2: accepted. The owner chose (2026-11-23) "Count, don't store": late and future-dated stream items are counted
  and never stored, so they cannot take a prompt copy's key (D18).
- C3: accepted. Pipeline-counted `icinga2_sync_progress`, a `stalled` phase, and a pipeline-owned resync sequence
  served by number (D12).
- C4: accepted. A dedicated consumer connection with a closed-client check and keepalives, closed at stop; no
  `pg_terminate_backend`; one 10 s budget for all consumers (D13).
- C5: accepted. The write boundary is a newer generation; the local deadline counts from the renewal's send time
  (D4).
- C6: accepted. The owner chose (2026-11-23) "Drop empty sync rows"; the watermark stays with change 7 as an
  interim exception recorded in ADR 0030 (D19).

  password publication (D8).
