## Findings

### Critical (blocking)

1. **Silent reconcile breaks the equal-start ordering contract for copies of one result.** On empty state, use an eligible stream OK received at 10:01, a distinct stream CRITICAL at the same projected start received at 10:02, and a sync copy of the OK received at 10:03. Process stream OK → sync OK → CRITICAL: the spec makes the sync a duplicate, so CRITICAL wins. Process sync OK → stream OK → CRITICAL: D2 creates an unkeyed tombstone with the 10:03 fence, so CRITICAL is stale. These are the same three rows, not a clock fault. D1 narrows the latest-*upstream*-result guarantee, but the equal-start requirement and main `alert-state` spec still promise deterministic ordering and first-carrier evidence. Define how a silent result participates in dedup and tie-breaking. Test both schedules and assert the final fence and published events.

2. **D2 reverses the existing observation-key/alert lock order.** A stream transaction first reserves event ID `K` and then waits for alert `F` (`pipeline.dart:445–495`; `alert_state_service.dart`, `apply`). A concurrent sync of `K` can hold `F`, decide that it repairs the alert, and then wait to reserve `K`, because D2 moves reconcile key insertion after the state decision. Fingerprint sorting does not prevent this cycle. The existing retry path treats deadlocks and lock timeouts as transient without consuming the attempt budget (`pipeline.dart:740–816`); under contention a repair can miss its application deadline without producing a failure-triggered resync. Specify one lock hierarchy for ordinary and reconcile rows without leaving a key for a silent item. Prove the overlapping stream/sync case with independent connections.

3. **D12 does not define an atomic sync terminal transition or preserve accounting for late completions.** If the pipeline finishes the last row before the holder writes `readEndAt`, the pipeline sees `reading` and cannot mark `complete`; the holder is specified to move to `applying`, with no subsequent completion writer. A failed row can also set `failed` while reading is open, which the unconditional `reading` → `applying` instruction does not handle. Separately, a transiently failing raw row can outlive D12’s 30-day progress prune: its eventual completion then has no counters to update, and D19 can remove the raw outcome. Define a guarded finalization rule run by both closing admission and terminal row processing, including zero-row syncs, failure precedence, and retention while admitted work remains outstanding. Preserve `holder_lost` and committed counts through late completions.

4. **A single persistent bad object can exhaust the failed-row cap without new stream traffic.** D3 retains one failed row for the object on each enumeration. D12 schedules another sync on each failure; the state machine also reconnects on sync failure, and D3 syncs on every reconnect. At the cap, even unrelated valid recoveries cannot be admitted. This release provides no normal drain for failed rows; changing the bad object upstream does not clear the cap. Separately, the five-minute resync requirement is conditioned only on database reachability, even when no holder can subscribe or admission is paused. Keep the owner’s retained-work cap, but distinguish deterministic bad input from a failed apply that another sync can repair. Specify when a request stays pending, how suppression is visible and how the source can recover. Test repeated syncs with one persistent error, then remove it and verify an unrelated recovery.

5. **D19 reduces steady-state retention but does not establish the claimed interim storage bound.** The pipeline retains every stream row and every sync row that stores any event. A healthy pipeline can keep `pending + failed` below the cap while hour after hour of syncs retain one repair-bearing row per batch. D7’s “one sync’s rows per source” is therefore not a bound; growth can exhaust the shared database while this source never pauses. Keep the owner’s decision to drop eventless rows, and state a measurable interim activation or storage limit, or explicitly approve and document unbounded retained growth as the ADR 0016 exception. Also resolve deletion timing: D19 deletes each eventless row in its processing transaction; the stream spec waits for `complete` or `failed` and says to delete the rows in one transaction, leaving `stalled` unspecified.

6. **D13 still promises database lock release its mechanism cannot guarantee.** Closing a dedicated socket removes the pooled-PID hazard, but the client check interval is not a deadline for a backend to finish rollback. TCP keepalives also do not bound every partition: a connection with unacknowledged data can be governed by retransmission rather than the idle keepalive schedule. D13 measures 15 seconds from the last packet; the spec measures it from stop. Development and test use `dataPath`, and the vendored Serverpod configuration skill says those connections use Unix sockets, where TCP keepalives do not apply. Separate the enforceable local stop deadline from backend cleanup guarantees; specify the dedicated connection’s transport and effective Serverpod settings, including external TLS. The current running-statement scenario waits on a lock that already has a two-second timeout, so it cannot prove socket-driven cancellation. Exercise active SQL and a partition separately.

7. **The local lease deadline has no initial anchor and the delayed-ack scenario ignores the preceding deadline.** D4 arms closure from the last successful *renewal*, but the holder subscribes immediately after acquisition. If the database disappears before the first renewal, no stated rule arms the timer, and a live old reader can survive the first takeover. On a running lease, a renewal sent at second 10 and acknowledged at second 22 cannot extend a deadline that expired at second 20. Specify the acquisition send time as the initial anchor, never revive a closed connection on a late reply, and test both cases. The durable generation fence does not close either socket.

### Moderate

1. **The convergence and divergence requirements omit cases the design already permits.** Under `hard_only`, a recent SOFT CRITICAL with a strictly later start than every preceding result is intentionally skipped, yet “Ordering holds within the clock and lateness limits” promises convergence to it. Also, the main `source-ingress` spec permits explicit namespace sharing; a webhook or another stream source can advance the same alert’s fence, defeating an unconditional per-object promise for one stream. Scope convergence to eligible, delivered, policy-applicable evidence and state the competing-writer condition. Specify whether a policy-skipped sync disagreement increments `diverged`.

2. **The retained-work count has no bounded access path.** `schema/0001_ingest.sql:1–15` indexes `(status, next_attempt_at)`, not `source_id` plus retained status. `LIMIT max_pending_rows + 1` bounds matching rows returned, not rows visited: a quiet source can repeatedly scan other sources’ retained work on every flush. Specify the index and schema path, and check admission latency for a quiet source beside a large unrelated backlog. Two other resource estimates are false as written: the minimum periodic interval is 300 seconds (288 syncs/day, not 24), and `objects / 100` is a best case, not a row bound under timed or byte-limited flushes.

3. **The sync scanner promises recovery beyond its framing evidence.** A string/nesting scanner can continue after a well-framed element that fails validation. It cannot reliably find the next element after an unterminated string or unmatched delimiter; D3’s unqualified “malformed element” scenario promises otherwise. Separately, a stable response whose tail never fits the 15-minute deadline restarts at the same prefix on every reconnect, so the tail can stay stale indefinitely. Define which malformed inputs are recoverable, when framing failure aborts, and how operators identify an installation that cannot enumerate fully within the deadline. Test both a framed invalid element and broken framing.

4. **Persisted nested diagnostics still do not carry the archived redaction rule.** D6 says to report the dotted path; `pipeline.dart:94–145` neither allowlists `check_result` and `vars_after` nor distinguishes a rendered sender-chosen name from structural segments after splitting on dots. The review-answer table mentions structural `*`, but the normative delta lacks it and the matching persisted-path scenario. Require structural redaction before rendering and test an unknown dotted key made entirely of allowlisted segments, plus the exact persisted path for duplicate `check_result.vars_after.state`.

5. **The secret inventory context misidentifies its sources, and the backfill has no bounded publication path.** `config_repository.dart:186–246` inserts output commitments into `ingest_secret_commitment` without replacing them; live credentials reside in `ingest_source_credential`. Snapshots are not the *only* surviving location for signing commitments: the same file at `:335–357` reads pinned webhook commitments from outbox. D8 now names snapshots, commitment rows and pins, addressing the original missing-snapshot case. Correct the evidence and specify how backfill completes on a populated database without an unbounded scan/write under the publication advisory lock. The marker and inventory must not claim completion across a crash or concurrent publication with a missed digest.

6. **The merged specs still leave contradictory baseline paths.** `durable-pipeline` “Atomic raw processing outcome” still requires raw `done`, while D19 removes the row in that transaction. The unchanged `alert-state` “Late duplicate of a ready observation” requires `duplicate_observation`, whereas the new stream scenario requires `late` with no key write even when the prompt copy went first. Scope the affected existing scenarios and requirements, and record ADR 0030’s actual exceptions to ADR 0017’s late/stale storage and dedup-before-state rules and ADR 0029’s credential-per-source rule. The draft ADR list does not cover them.

7. **The test map remains absent and some THENs cannot prove their claims.** No `tasks.md` or scenario-to-task map was present; the roadmap still names `CheckResult` (`openspec/roadmap.md:42`). “Persistent bad object before a missed recovery” says *each* sync resolves the same alert, without refiring between runs. “Insert blocked below the cap” waits 30 seconds on one insert lock despite D5’s two-second lock timeout. Specify a cumulative blocked-reader scenario, assert the first repair and subsequent absence of duplicate repair, and map reproducible release, database and cancellation cases to automated evidence. Replace the prose-reading limits check with behavioral checks where the limits are executable. Leave only the real-installation exercise with the owner.

8. **The carried constraints omit the boundaries future changes are most likely to undo.** C2 carries fenced admission but not no-renew-after-expiry, the acquisition/renewal send-time deadline, or the distinction between expiry and generation grant. C13 calls D18 and D19 interim exceptions until change 7, even though D18 rejects storing late copies because they can reserve the ID of a prompt recovery. No carried entry preserves the rejection of a connection idle timeout for a healthy quiet stream. Give each invariant one durable destination, and separate the permanent key-safety rule from the temporary storage-watermark exception.
