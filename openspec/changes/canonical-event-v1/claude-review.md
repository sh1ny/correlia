## Verdict

**APPROVE_WITH_CHANGES. The plan should be simplified before apply.**

The identity core is correct and well specified. I recomputed the design's complete fixture independently, using Python `hashlib` and `uuid` with the documented `E(...)` encoding:
- fingerprint `09fc69bd…137b7f`: matches;
- base64 `observation_key`: byte-equal to `E(domain, status, starts_at=0x01‖text, ends_at=0x00)`;
- event id `4d8c0cd4-4b0f-5985-b773-f83322c61006`: matches.

The standard CloudEvents envelope and the protobuf payload are sound choices and follow ADR 0004.

The plan goes well beyond the approved requirements in three mechanisms:
1. a custom descriptor-to-JSON-Schema compiler with a Correlia-owned options vocabulary (D1);
2. a multi-minor, append-only compatibility manifest with a semantic checker for frozen value domains (D5);
3. opaque preservation of unknown JSON fields with cross-representation rules, and a mandatory dataschema for binary input (D6).

ADR 0004 and UPG-3 ask for less: protobuf as the source of truth, a generated JSON Schema, `buf breaking` as the gate, additive minors, and "older consumers still parse". About half of the task plan (2.1, 2.3, 4.3, 5.1–5.3) is effort spent on these inventions. Off-the-shelf tools cover most of D1. D5 and D6 can be reduced to what v1.0 needs now.

The envelope's closed schema also conflicts with how CloudEvents handles extensions (F4). Before apply, fix F4 and F6, and adopt or reject F1–F3 explicitly.

## Findings

Severity: **High** means it should change before apply; **Medium** means it should be decided before apply; **Low** means fix during apply or note it.

### F1 — High: replace the bespoke descriptor compiler and options vocabulary with `buf.validate` and `protoc-gen-jsonschema`

*Refs: design D1, "Generation and compatibility flow" ¶3–4, Mechanism Ledger row 3; tasks 2.1–2.3; workspace-tooling "Reproducible event contract generation".*

The Mechanism Ledger says "Official generator offering the exact local format could replace implementation." I checked whether one exists. It does:
- **`bufbuild/protoschema-plugins`** (Buf, active, last push 2026-11-09, release v0.6.0 of 2026-04-28) ships `protoc-gen-jsonschema`. It emits JSON Schema draft 2020-12 using JSON field names. It reads `buf.validate` annotations (required, ranges, string rules). Its `*.jsonschema.strict.json` variant sets `additionalProperties: false` and rejects aliases and non-normalized representations (README; `internal/testdata/jsonschema/…RequiredOptional.jsonschema.strict.json`).
- **Protovalidate** (`buf.validate`) is a standard constraint vocabulary that already covers the design's rule list:
  - `StringRules` has `min_len`/`max_len` (characters), `min_bytes`/`max_bytes`, `pattern`, `const` and `in`;
  - there are also map and repeated pair/item limits and integer ranges (Context7 `/bufbuild/protovalidate`).

  Official runtimes exist for Go, Java, Python, C++ and ES, but **not for Dart**.

**Impact.** D1 builds and maintains three things: a constraint language, a JSON Schema compiler and a compatibility-aware option checker. The generator also fails closed on any proto shape it does not support. For non-Dart consumers, standard annotations are strictly better. The Go NATS output plugin (ADR 0018) could validate with `protovalidate-go` at no extra cost. A Correlia-private option gives them nothing.

**Smallest design:**
- annotate `event.proto` with `buf.validate`;
- generate the strict JSON Schema with a pinned `protoc-gen-jsonschema`, installed through the already-pinned Go 1.27.3 (`go install …@vX.Y.Z` into a tool-local `GOBIN`, or a Buf `local:` plugin entry);
- for Dart runtime bounds, take the cheaper of two options:
  - (a) a small generated Dart constants file, produced by a script that reads the `buf build` image (JSON format) for the fields that carry `buf.validate` rules;
  - (b) a handwritten Dart bounds table plus one fast test asserting it equals the annotations in the image.

Option (b) satisfies D1's "no silent divergence" goal. It does so with a failing test rather than a compiler.

**Unverified; prove it in a spike before committing:**
- whether `protoc-gen-jsonschema` uses an explicit snake_case `json_name` when it is set;
- how it renders `uint64` (as a string), `Timestamp`, `bytes` and maps with `max_pairs`;
- whether it can express the envelope.

Where the output is wrong, a small post-processing step is still far smaller than a compiler.

### F2 — High: treat the CloudEvents envelope as a small fixed codec, not a protobuf message with generated schema

*Refs: design "Payload and envelope" ¶"Envelope message fields…", D1 ("The CloudEvents envelope is defined in the same proto tree as an envelope message with fixed-value options"), "Generation…" ¶3 ("The custom compiler emits the envelope's `$defs`").*

The envelope is a standard document of about 12 attributes and does not change between Correlia minors:
- two constants;
- six values derived from the payload (`id`, `source`, `type`, `subject`, `partitionkey`, `correliatenant`, `time`);
- an optional `traceparent`;
- `dataschema`;
- the `data` object.

Modelling it as a proto message with fixed-value options adds options vocabulary, compiler support and compatibility rules for something the contract never evolves. It also suggests a binary envelope, which the design then has to disclaim.

**Smallest design:**
- write a handwritten Dart `CloudEventEnvelope` encoder and strict reader, roughly 150–250 lines with sealed errors, that derives every attribute from the validated payload and checks agreement on read;
- if an envelope JSON Schema is wanted for external consumers, write one short handwritten file whose `data` is a `$ref` to the generated payload schema. Do not copy the CloudEvents project's schema: AGENTS.md forbids copying third-party schemas.

This keeps one generated artifact, the payload schema, as ADR 0004 asks.

**Existing Dart libraries.** I verified both from primary sources, because Context7 indexes neither.
- `functions_framework` 0.4.3+1 (Google, last published 2023-08-13) exports `CloudEvent` (`lib/src/cloud_event.dart`). It is unsuitable as a dependency:
  - **extensions are dropped.** The model has no extension map, and the generated `fromJson` checks only required keys, so `partitionkey`, `traceparent` and `correliatenant` vanish on read;
  - `time` is a `DateTime`, so nanoseconds are lost, against D3;
  - `data` is `Object?`, with no `data_base64` rejection and no strictness;
  - it pulls in a FaaS runtime (`shelf`, `http`, `google_cloud`, `json_annotation`, `io`) for one model class.

  It is useful only as a reference for attribute names.
- `google_cloudevents_dart` 0.0.2 (community, 2024-03-29, 1 like, 24 downloads in 30 days) contains generated Google *Eventarc payload* protos plus Google option extensions (`cloudevent.pb.dart`: `ExtensionAttribute`, `cloudEventType` options). It has **no envelope codec**. It also depends on `protobuf: ^3.1.0`, which cannot coexist with the planned `protobuf 6.1.0` pin, and on `analyzer: ^6.4.1`. Reject it.

Conclusion: neither package meets the extension, precision or payload requirements. The envelope is small enough that handwritten code is the right size, provided the scope is limited to F2.

### F3 — High: cut D5's compatibility machinery to what v1.0 needs

*Refs: design D5, "Generation and compatibility flow" ¶4–5, State & Ownership row 3; workspace-tooling "Event compatibility gate" (6 scenarios); tasks 5.1–5.2.*

ADR 0004 and UPG-3 require `buf breaking` and additive minors. D5 adds:
- an append-only manifest of every published minor's image, schema and digest;
- verification that main's manifest is an unchanged subset;
- comparison against *all* historical images;
- a semantic differ for Correlia constraint options;
- a "candidate equals latest" publication check;
- synthetic v1.0/v1.1/v1.2 Buf histories in tests.

At v1.0 there is exactly one published version. Most of this machinery protects against histories that do not exist yet, and it is tested only with synthetic fixtures. The approved round-2 fixes (M4/M5 in `review.md`) added the frozen-domain and later-minor scenarios, which explains how the scope grew.

**Smallest design that keeps the real protection:**
1. Commit `contracts/baselines/event-v1.0.binpb` once. In `proto:check`, run `buf breaking --against contracts/baselines/event-v1.0.binpb` with FILE rules. A digest file is optional: git history already makes an edit to the baseline visible in review.
2. Freeze value domains with a **snapshot test**: commit the extracted `buf.validate` rules of every v1.0 field (JSON from `buf build -o …#format=json`) and fail when any existing field's rules differ. This covers "summary 256 → 512 fails" without a semantic differ.
3. Defer the multi-minor manifest and the main-subset check to the change that publishes v1.1, when there is real history. Record the deferral in the planned ADR.

This drops the four `proto_compatibility_test` scenarios that need synthetic multi-minor histories. "Add optional bounded field" and "Break existing consumers" remain testable against the single baseline.

### F4 — Medium: the closed envelope conflicts with CloudEvents extension semantics

*Refs: design "Payload and envelope" ("Exact-version schemas reject other properties"), "Forward parsing"; canonical-event "Extensions have one location".*

CloudEvents puts all extension attributes at the top level of the JSON document (JSON format §2; Primer "JSON Extensions"). It also states that an intermediary SHOULD forward OPTIONAL attributes (spec v1.0.2 §"Intermediary", line 55). Brokers and bridges legitimately add extension attributes. The design rejects any undeclared top-level attribute in "exact v1.0" input, and it keys envelope strictness to the *payload's* `dataschema` minor. An extension added by an intermediary is not a Correlia minor change, so a valid CloudEvent carrying, for example, a broker's tracing extension would be rejected.

**Recommendation:**
- keep the payload (`data`) strict for exact minors;
- on the envelope, reject only these:
  - malformed declared attributes;
  - `data_base64`;
  - attribute names outside `[a-z0-9]{1,20}`;
  - a top-level copy of a *payload* extension key such as `example.org/context`. That key's `/` and `.` already make it an invalid CloudEvents attribute name, so the name rule catches it;
- ignore unknown, well-formed extension attributes, or preserve them as an opaque string map.

This keeps the "Extensions have one location" scenario and removes the interoperability failure.

### F5 — Medium: D6's forwarding and provenance machinery exceeds UPG-3

*Refs: design D6, "Forward parsing", "Binary reader provenance"; canonical-event "Version aware validation…" and "Explicit binary schema provenance"; tasks 4.1, 4.3.*

UPG-3 reads: "`buf breaking` passes; older consumers still parse".
- Protobuf binary consumers keep unknown fields natively; `UnknownFieldSet` comes free.
- The Dart runtime's ProtoJSON does **not** keep them. `toProto3Json` documents "Unknown field data … will not be included". `mergeFromProto3Json` either throws or ignores unknown fields (`ignoreUnknownFields`, protobuf 6.1.0 `generated_message.dart:275-318`).

The design therefore needs bespoke code for every one of these:
- an immutable opaque JSON tree at every nesting level;
- re-emission in the original representation;
- a transcoding error;
- a mandatory `sourceDataschema` for binary reads;
- provenance in forwarding results.

M1 has no Dart component that *forwards* a newer-minor event. Correlia is the producer, and the raw inbox (ADR 0016) keeps original bytes.

**Smallest design:**
- the JSON reader chooses strict mode (exact supported minor) or `ignoreUnknownFields: true` (newer v1 minor) from `dataschema`, and reports `validationScope: knownCoreOnly`;
- protobuf parsing keeps `UnknownFieldSet` as the runtime already does;
- make `sourceDataschema` an *optional* argument of the binary reader. When it is absent, the result scope is `unknown`, and no exact-minor claim is made.

Defer opaque JSON preservation and cross-representation rules until a forwarding consumer exists. That keeps UPG-3 provable with one v1.1 fixture per representation.

If the owner wants lossless JSON forwarding in v1, keep D6. But record it as an explicit scope decision, because it is the single largest piece of handwritten JSON code in the change.

### F6 — Medium: Dart cannot validate draft 2020-12 JSON Schema, so the fixture-validation tasks have no tool

*Refs: proposal Impact ("JSON Schema validation dependencies"), tasks 2.3, 4.4, 6.1 ("validates the exact schema").*

`json_schema` 5.2.2 (Workiva), the main Dart validator, documents support up to Draft 7 in its README. The design emits draft 2020-12, as does `protoc-gen-jsonschema`. The plan does not say what validates the committed fixtures against the generated schema.

**Choose one before apply:**
- validate fixtures in `tool` tests with a pinned validator that runs under the already-pinned toolchains: Node 24 or Go 1.27.3. Verify the exact package and version during apply; I did not verify one;
- or require the generator to emit Draft 7.

Do not plan Dart runtime schema validation. The Dart reader is a handwritten strict walker anyway (F7).

### F7 — Low: the Dart ProtoJSON reader is lenient; the strict pre-pass is required, not optional

*Refs: design D3 ("Reject numeric enums, aliases, nulls and implicit coercions at the strict JSON reader"), contract "Timestamps use RFC3339…".*

This confirms the design rather than criticising it. Protobuf 6.1.0 has several lenient behaviours:
- Timestamp parsing uses `DateTime.tryParse` after removing the fraction (`mixins/well_known.dart:264-298`). That accepts input without an offset, which it treats as local time, and Dart rolls invalid calendar dates over instead of rejecting them;
- `supportNamesWithUnderscores` defaults to `true`;
- `permissiveEnums` exists as an option.

The strict reader therefore has to validate the JSON tree before calling `mergeFromProto3Json`:
- RFC 3339 with an explicit offset, a calendar check and no leap seconds;
- exact keys and no nulls;
- enum name strings;
- `uint64` as a decimal string.

On output, `toProto3Json` writes `fieldInfo.name`, which is the protoc `json_name` (`field_info.dart:14-20`), and Timestamps keep up to 9 fractional digits. Explicit snake_case `json_name` works as the design intends. Keep this pre-pass in task 4.3; it should not be cut.

### F8 — Low: the `package:uuid` fallback is unnecessary

*Ref: design D4 ("UUIDv5 can use package:uuid's byte API or a short RFC implementation if it cannot accept arbitrary name bytes").*

`uuid` 4.6.0 (2026-07-15) provides `Uuid().v5FromBytes(String? namespace, Uint8List? name)` (`lib/uuid.dart:546`, `lib/v5.dart:72-86`). It is documented for arbitrary binary names under RFC 4122/9562, which the binary `observation_key` needs. Pin `uuid: ^4.6.0` and `crypto` (3.0.8), and drop the "short RFC implementation" branch. Keep independent vectors, as D4 requires; the Python recomputation above is a ready template.

### F9 — Low: the 256 KiB event cap is above the CloudEvents safe-forwarding size

*Refs: design "Field and work bounds" (262144 bytes), canonical-event "Bounded event fields".*

CloudEvents 1.0.2 "Size Limits" says intermediaries MUST forward events of 64 KByte or less, and consumers SHOULD accept at least 64 KByte. Larger events are not guaranteed through generic intermediaries. NATS's default limit is larger, so M1 is unaffected.

Document in the planned ADR that events above 64 KiB rely on the transport, or lower the cap. With 128 labels × 1 KiB plus annotations, a realistic upper bound already exceeds 64 KiB.

### F10 — Low: the 256 KiB cap contradicts ADR 0004's "a schema-valid input never fails later on length"

*Refs: ADR 0004 "Bounds"; design "Risks" ("JSON Schema cannot express … total UTF-8 bytes").*

An event can pass the generated schema field by field and still exceed the total byte cap at runtime. The design acknowledges this. The new ADR planned in task 1.1 should state it explicitly as a refinement of ADR 0004's sentence: schema validity is necessary, not sufficient. This avoids a silent conflict with an accepted ADR.

## Concrete simplifications (in priority order)

1. **F1:** `buf.validate` annotations plus a pinned `protoc-gen-jsonschema` (strict). Use a Dart bounds table that is generated or cross-checked by a test. Delete `proto/correlia/contract/v1/options.proto` and the descriptor compiler. Prerequisite: a short spike that checks its output against D3 (json_name, uint64, Timestamp, bytes, maps).
2. **F2:** a handwritten Dart envelope codec. Make the envelope schema optional and handwritten with `$ref` to the payload schema, and keep the envelope out of proto. Do not depend on `functions_framework` or `google_cloudevents_dart`.
3. **F3:** one committed v1.0 baseline, `buf breaking` with FILE rules, and a snapshot test of the existing fields' validate rules. Defer the manifest and multi-minor history to the v1.1 publication change.
4. **F5:** the reader selects strict or ignore-unknown by `dataschema` minor and reports its scope. Binary `sourceDataschema` is optional. Defer opaque JSON preservation and transcoding rules.
5. **F4:** a tolerant envelope for well-formed unknown CloudEvents extension attributes, and a strict `data`.
6. **F8:** use `uuid.v5FromBytes`.

Together these remove roughly the custom compiler (tasks 2.1/2.3 core), most of 5.1/5.2, and the opaque-tree half of 4.3. They keep every ADR 0004/0019 requirement and every ID-4/ID-6/ID-7(b,c)/UPG-3 acceptance scenario.

## Remaining risks

- **Identity bytes are irreversible once published.** The encoding is unambiguous, and I reproduced it independently. One edge case is untested: the native-key tag byte and the `0x00`/`0x01` component tag inside nested `E()`. Commit at least one vector for each domain (native, fallback, transport header and body), not only the Alertmanager example.
- **The `protoc-gen-jsonschema` output shape is unverified for this contract** (F1). If the spike shows gaps, a small post-processor is the fallback, not the full compiler.
- **Spec churn:** F3 and F5 change scenarios that `review.md` rounds 2–3 accepted (M4/M5). Under `decision_making: autonomous` these are agent decisions and can change, but the reasoning should be recorded against D5/D6 so that M4/M5 are not silently reopened.
- **Dart has no protovalidate runtime.** Dart-side bounds stay handwritten or generated. Drift is then prevented by the test or the generator in F1, not by the vocabulary.
- **Dependency pins:** `protoc_plugin` 25.1.0 and `protobuf` 6.1.0 are confirmed current on pub.dev (both 2026-09-11). Serverpod 4.1's transitive constraints were not resolved here, because no `pub get` was run, so compatibility with the workspace lock still has to be proven in task 2.2.
