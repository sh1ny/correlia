## Phase Goal

**As a** Correlia operator, **I want to** recover, expire, inspect, and mutate incidents through backend APIs and operability signals, **so that** the v1 operational surface is complete without a built-in frontend.

<objective>
Complete operability with safe JSON structured logs, expanded `/v1/readyz`, and final targeted verification readiness. This plan finishes Phase 04's non-secret operational surface after lifecycle, API, and metrics slices exist.

Purpose: Operators need enough safe signals to diagnose Correlia without leaking secrets or relying on a UI. Maintainers need exact targeted verification commands for the completed backend surface.
Output: JSON logging helper/configuration, safe log calls at critical seams, expanded readiness checks, and targeted logging/readiness/coverage tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Runtime processing -> log sink | Operational events leave process memory as JSON logs. |
| Readiness dependencies -> REST client | Internal state/config/plugin/worker health is exposed through `/v1/readyz`. |
| Test/verification commands -> maintainer workflow | Targeted commands prove behavior without substituting SQLite or running broad gates. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-05-I | Information Disclosure | JSON logs | mitigate | `SAFE_LOG_KEYS`, `safe_log_extra()`, no `logger.exception`, no `exc_info`, and tests blocking raw payloads, secrets, credentials, SMTP transcripts, stack traces, rendered bodies, and plugin options. |
| T-04-05-R | Repudiation | operator/recovery/expiration logs | mitigate | Emit structured safe ids/reasons/counts at mutation boundaries: incident id, rule_name, group_key, status, severity, effect, reason/category, operator where provided. |
| T-04-05-D | Denial of Service | log volume/content | mitigate | Log one bounded event per boundary and avoid raw bodies or unbounded exception strings; use existing log level setting. |
| T-04-05-I2 | Information Disclosure | `/v1/readyz` failure details | mitigate | Return safe check names/statuses only; do not include DB URL, file contents, plugin options, exception text, stack traces, or credentials. |
| T-04-05-T | Tampering | readiness result correctness | mitigate | Ready requires database check success, configured config state, plugin readiness, and lifecycle worker health; tests cover each failure mode. |
| T-04-05-HIGH | ASVS L1 high-severity gate | logs/readiness | mitigate | No high-severity threat is accepted; block if any log or readiness response leaks raw/secret/stack trace data. |
</threat_model>
