## Phase Goal

**As a** Correlia operator, **I want to** have accepted PROBLEM events become durable topology-aware incidents and dispatch notification work only on durable threshold transitions, **so that** an alert storm produces one accurate incident and one controlled notification path.

<objective>
Wire the complete Phase 03 vertical slice: Icinga2 PROBLEM webhook → normalization/enrichment/rule decision → durable incident aggregation → post-commit TaskRunner notification submission → output plugin dispatch/failure recording → compact API response and plugin listing.

Purpose: This completes the phase goal while preserving the locked ordering: durable incident and threshold marker write first, commit second, TaskRunner submission third.
Output: Notification dispatcher, ingress/main/dependency wiring, plugin listing router, failure recording, and end-to-end targeted tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP webhook → processing pipeline | Untrusted Icinga2 request data flows into normalization, topology, rules, incident aggregation, and response. |
| Durable incident transaction → TaskRunner | Output work must not observe or announce uncommitted incident state. |
| TaskRunner payload → NotificationDispatcher | Plain payload values select incident id and plugin name for background dispatch. |
| Output dispatcher → plugin/SMTP | Plugin code and external SMTP can fail after the ingest response path. |
| Plugin registry → REST listing | Configured plugin status is exposed through an API route. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-03-R | Repudiation | `IncidentManager.apply_problem` ordering | mitigate | Source-order and behavior tests require commit before `TaskRunner.submit`; notification payload includes incident id, rule/group, plugin name, and config hash. |
| T-03-03-I | Information Disclosure | notification failure results | mitigate | Closed categories and bounded sanitized messages only; no exception traces, credentials, SMTP transcripts, rendered bodies, raw payloads, or plugin options in API/decision_context. |
| T-03-03-D | Denial of Service | repeated notifications | mitigate | Dispatch only on `first_threshold_transition`; below-threshold, replay, and already-notified branches never submit tasks. |
| T-03-03-T | Tampering | task payload plugin selection | mitigate | Validate payload with `NotificationTaskPayload`, resolve plugins from trusted cached registry names, and reject missing plugin safely. |
| T-03-03-D2 | Denial of Service | background task failure | mitigate | Runner retrieves exceptions; dispatcher records safe result with a fresh session; lifespan drains tasks on shutdown. |
| T-03-03-E | Elevation of Privilege | `/plugins` route | mitigate | Route lists safe status only and does not expose executable config, options, credentials, or module internals. |
</threat_model>
