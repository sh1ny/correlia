## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Domain model -> repository | Validated incident facts cross into persistence code and must stay bounded/secret-safe. |
| Repository -> PostgreSQL | SQLAlchemy emits the single atomic write statement; values may contain operator/source-derived strings. |
| Test runner -> PostgreSQL | Testcontainers verifies real PostgreSQL concurrency/index behavior. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-20 | Tampering | `upsert_open_incident` | mitigate | Use PostgreSQL `insert(...).on_conflict_do_update(... index_where=(Incident.status == IncidentStatus.OPEN.value))`; tests assert no SELECT-then-INSERT source path. |
| T-01-21 | SQL injection | Repository values | mitigate | Use SQLAlchemy bound values and fixed dialect expressions only; injection-shaped rule names are persisted literally and table existence is verified after upsert. |
| T-01-22 | Information disclosure | `decision_context` persistence | mitigate | Accept only Plan 01-02 `DecisionContext.model_dump(mode="json")`; tests reject raw payload and secret-shaped metadata before DB execution. |
| T-01-23 | Denial of service | JSONB affected sets | mitigate | `MAX_AFFECTED_HOSTS = 100`, `MAX_AFFECTED_SERVICES = 100`, sorted/deduped arrays, and tests for the 100-item bound. |
| T-01-24 | Tampering | Severity max | mitigate | Explicit rank mapping `OK=0`, `WARNING=1`, `UNKNOWN=2`, `CRITICAL=3` and SQL CASE update prevent latest-event downgrade. |
| T-01-25 | Elevation of privilege | YAML parser safety | accept | This plan does not parse YAML and must introduce no `yaml.load(` calls. |
| T-01-26 | API exposure | Repository | accept | This plan creates no auth-independent HTTP mutation endpoint. |
</threat_model>
